# Research: self-hosted OTLP-native observability backend for several hobby projects

Resolves GitHub issue #23. Researched 2026-09-17 against primary sources only (project docs, GitHub repos, license files, Compose files, OpenTelemetry and Cloudflare docs). Extends, and does not repeat, `docs/research/observability-analytics.md` (Grafana Cloud vs OpenObserve Cloud, browser SDK options). The event model under evaluation is `docs/spec/observability.md`: OTLP/HTTP **JSON** from a Cloudflare Worker (Effect `Otlp.layerJson` plus Cloudflare's platform exporter) and from the OpenTelemetry web SDK; analytics events are log records with `event.name`; one gauge metric.

## Summary

- All five candidates ingest traces, logs and metrics over OTLP/HTTP and all five accept the JSON encoding, so the vendor-neutral event model survives unchanged; only `OTEL_EXPORTER_OTLP_ENDPOINT` and one auth header differ per backend.
- Only OpenObserve is a single process with built-in login, TLS switches and multiple organisations in the free edition; every other candidate needs 4 to 5 containers and pushes ingest auth and TLS to a reverse proxy, or gates tenancy behind enterprise (SigNoz, HyperDX).
- No project documents a measured footprint at hobby volume. SigNoz and HyperDX publish "at least 4 GB RAM" minimums; Uptrace's smallest sizing row is 24 vCPU / 48 GB; Grafana and OpenObserve publish none. A 2 GB VPS is therefore only realistic with OpenObserve, and 4 GB is the floor for the ClickHouse-based stacks.
- Product-analytics questions are answered by SQL or query-builder panels everywhere; none of the five has funnels over log records (SigNoz's funnels are span-only), so funnels stay hand-built.
- Recommendation: self-hosted OpenObserve as the one backend, SigNoz as the fallback if a 4 GB VPS is acceptable and the query builder matters more than tenancy; Grafana Cloud Free remains the stopgap until the VPS exists.

## Findings

### 0. Wire-format constraints that apply to every candidate

- OTLP/HTTP paths are `/v1/traces`, `/v1/metrics`, `/v1/logs`; JSON payloads use `Content-Type: application/json`, with `traceId`/`spanId` hex-encoded and enums as integers. The spec says servers "SHOULD accept" binary Protobuf and JSON on the same port; JSON support is not mandatory, so it has to be checked per backend. Source: https://opentelemetry.io/docs/specs/otlp/
- The OpenTelemetry Collector `otlp` receiver (which SigNoz, HyperDX/ClickStack, Tempo and Grafana Alloy embed) accepts OTLP JSON on port 4318 and has a `cors` block (`allowed_origins`, `allowed_headers`) that browsers need. Sources: https://github.com/open-telemetry/opentelemetry-collector/blob/main/receiver/otlpreceiver/README.md and https://grafana.com/docs/alloy/latest/reference/components/otelcol/otelcol.receiver.otlp/
- Cloudflare's platform exporter is configured in the dashboard with a destination URL plus custom headers, exports traces and logs only, states "Cloudflare does not support the Binary format for OTLP ingest", and the URL must carry the full signal path (for example `.../v1/traces`); Cloudflare does not append it. Workers Traces are in beta with billing from 2026-10-01 (Workers Free: 200k events/day, 3-day retention; Paid: 20M/month included). Sources: https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/ and https://developers.cloudflare.com/workers/observability/traces/
- Browser side: `@opentelemetry/sdk-trace-web` plus `@opentelemetry/exporter-trace-otlp-http`, and `@opentelemetry/sdk-logs` plus `@opentelemetry/exporter-logs-otlp-http` (which "uses OTLP (http/json)", default `http://localhost:4318/v1/logs`, custom `headers` supported) run in browsers; the OTel docs still label browser instrumentation "experimental and mostly unspecified". Sources: https://opentelemetry.io/docs/languages/js/getting-started/browser/ , https://github.com/open-telemetry/opentelemetry-js/tree/main/experimental/packages/exporter-logs-otlp-http , https://github.com/open-telemetry/opentelemetry-js/tree/main/experimental/packages/sdk-logs

Consequences: whatever header a backend uses for auth ends up in browser-visible JavaScript, so each backend needs a low-privilege, per-project ingest credential; and every backend needs CORS opened for the site origin.

### 1. SigNoz

- OTLP: self-hosted exposes OTLP/gRPC 4317 and OTLP/HTTP 4318 through `signoz-otel-collector` (a Collector distribution), so JSON is accepted per the receiver README above. "Self-hosted/community edition of SigNoz does not use ingestion keys"; the docs tell you to put a reverse proxy (nginx, Traefik, HAProxy) in front and "enforce TLS and auth there". Browser telemetry needs the collector `cors` block. Source: https://signoz.io/docs/ingestion/self-hosted/overview/
- Cloudflare exporter: works once the collector is behind an HTTPS proxy; auth is whatever header the proxy checks.
- Stack and footprint: Docker Compose runs ClickHouse 25.5, ClickHouse Keeper, PostgreSQL 16, the SigNoz collector and the single `signoz` binary; "At least 4GB of memory allocated to Docker", no CPU or disk figure. The legacy `install.sh` and `deploy/` Compose files are deprecated in favour of Foundry (one config, one command, pinned dependency versions). Sources: https://signoz.io/docs/install/docker/ , https://signoz.io/blog/introducing-signoz-foundry/ . The capacity guide's smallest "production" table is 56 cores / 152 GiB across 10 nodes, which says nothing about hobby volume. Source: https://signoz.io/docs/setup/capacity-planning/community/resources-planning/
- Multi-project: a maintainer wrote on 2025-03-22 "We do not have a multi-tenant architecture today ... the feature will be available to enterprise users once it is available". Separation is by resource attribute filtering only. Source: https://github.com/SigNoz/signoz/discussions/7253
- License: MIT for everything outside `ee/` and `cmd/enterprise/`, which are under `ee/LICENSE`. Source: https://github.com/SigNoz/signoz/blob/main/LICENSE . Pricing lists "Fine-grained RBAC", "Security tightening for on-premise installation" and "Monitor Health of SigNoz" as Enterprise self-managed; SSO by email/password, OIDC and Google is in the product but "Availability depends on your plan". Sources: https://signoz.io/pricing/ and https://signoz.io/docs/userguide/authentication/
- Auth and TLS: UI has email/password sign-up, invites, Admin/Editor/Viewer roles. No TLS in-product; reverse proxy expected (above).
- Upgrade and backup: an Upgrade Path tool lists required version stops; "Pin the version at every required stop", wait for migrations between stops. Backup guidance is limited to the metadata SQLite/Postgres store; ClickHouse volumes are your own responsibility. Sources: https://signoz.io/docs/operate/upgrade/ and https://signoz.io/docs/operate/migration/upgrade-0.76/
- Product analytics over log records: the Logs API and query builder support filter, count and group-by over log attributes, and dashboards plot them. Trace Funnels count "sequential spans within the same trace" (span-only, available Cloud and Self-Host). Sessions and log-record funnels are hand-built ClickHouse SQL. Sources: https://signoz.io/docs/logs-management/logs-api/overview/ and https://signoz.io/docs/trace-funnels/overview/
- Browser RUM: plain OpenTelemetry web SDK (`sdk-trace-web`, `exporter-trace-otlp-http`, fetch/XHR/user-interaction instrumentations) posting to `http://<ip>:4318/v1/traces`; no proprietary SDK. Source: https://signoz.io/docs/frontend-monitoring/sending-traces-with-opentelemetry/

### 2. HyperDX (ClickStack)

- OTLP: the bundled Collector listens on 4317/4318 (JSON accepted per receiver README); open-source deployments require an `authorization: <ingestion API key>` header from Team Settings, and a standalone collector can enforce `OTLP_AUTH_TOKEN`. Signals: logs, metrics, traces, sessions. Sources: https://clickhouse.com/docs/use-cases/observability/clickstack/ingesting-data/opentelemetry and https://clickhouse.com/docs/use-cases/observability/clickstack/config
- Cloudflare exporter: works with the `authorization` header once the collector sits behind HTTPS.
- Stack and footprint: all-in-one image `clickhouse/clickstack-all-in-one` (ClickHouse + HyperDX + Collector + MongoDB) on ports 8080/4317/4318, with `/data/db` and `/var/lib/clickhouse` volumes, explicitly not for production; the Compose variant runs the same four services separately and is "suitable where fault tolerance isn't required and a single server is sufficient". README minimum: "4GB RAM and 2 CPU cores". Sources: https://clickhouse.com/docs/use-cases/observability/clickstack/deployment/all-in-one , https://clickhouse.com/docs/use-cases/observability/clickstack/deployment/docker-compose , https://github.com/hyperdxio/hyperdx
- Multi-project: before RBAC "all ClickStack users belonged to the same group" and isolation meant separate HyperDX instances; RBAC (2026-04-01) is "exclusive to Managed ClickStack". Open source therefore has one team per instance; separate projects by ClickHouse database/source or by attribute. Source: https://clickhouse.com/blog/role-based-access-control-clickstack
- License: MIT (copyright DeploySentinel, Inc.). Source: https://github.com/hyperdxio/hyperdx/blob/main/LICENSE
- Auth and TLS: UI credentials are created on first run; production guide says set `EXPRESS_SESSION_SECRET`, change the ClickHouse `default` user, expose only OTLP/API/UI ports, and "enabling TLS for OTLP endpoints is recommended" (via ClickHouse `config.xml` for the DB, a proxy for the collector). Source: https://clickhouse.com/docs/use-cases/observability/clickstack/production
- Upgrade and backup: no OSS upgrade or backup procedure is documented; "Managed ClickStack: Automated backups included". Retention defaults to 3 days via table TTL (`ALTER TABLE ... MODIFY TTL` or the exporter `ttl:` setting). Sources: same production page and https://clickhouse.com/docs/use-cases/observability/clickstack/ttl
- Product analytics: SQL and Lucene-style search over wide events, dashboards and alerts; no funnel primitive. Source: https://clickhouse.com/docs/use-cases/observability/clickstack/overview
- Browser RUM: `@hyperdx/browser` adds session replay, console and network capture and is what the Sessions view keys on; plain OTel web SDK data lands in logs/traces but the docs do not describe sessions without the SDK. Source: https://clickhouse.com/docs/use-cases/observability/clickstack/sdks/browser

### 3. OpenObserve (self-hosted)

- OTLP: `https://<host>/api/<org>/v1/{traces,logs,metrics}` with `Authorization: Basic base64(email:password)`; the organisation is the URL path segment; no trailing slash. The API reference lists `application/json` (OTLP JSON Protobuf Encoding) and `application/x-protobuf` as accepted content types. Sources: https://openobserve.ai/docs/ingestion/logs/otlp/ and https://openobserve.ai/docs/reference/api/ingestion/traces/otlp/
- Cloudflare exporter: works directly (HTTPS URL per org and signal, `Authorization` custom header); no collector needed.
- Stack and footprint: one binary or one container, `ZO_DATA_DIR` on local disk, port 5080; root user from `ZO_ROOT_USER_EMAIL`/`ZO_ROOT_USER_PASSWORD`. No RAM/disk minimum is published; the capacity-planning page defers to a spreadsheet; the HA guide says single-node local disk is not for production and gives no backup guidance for it. Memory knobs exist (`ZO_MEM_TABLE_MAX_SIZE` default 50% of RAM, `ZO_MEMORY_CACHE_*`). Sources: https://openobserve.ai/docs/quickstart/ , https://openobserve.ai/docs/environment-variables/ , https://openobserve.ai/docs/ha_deployment/ , https://openobserve.ai/docs/enterprise-setup/capacity-planning/
- Multi-project: organisations are "logical boundaries for separating data, users, and access controls", any authenticated user can add one in open source, and `ZO_CREATE_ORG_THROUGH_INGESTION` (default on) lets the root user create one by ingesting. Not enterprise-gated. Source: https://openobserve.ai/docs/user-guide/identity-and-access-management/organizations/
- License: AGPL-3.0 for the open-source edition; the Enterprise edition (SSO, RBAC, audit trail, federated search, PII redaction, BYOB) is a separate binary, free "up to 50 GB/day of ingestion ... including full commercial use", registration above that. Sources: https://github.com/openobserve/openobserve/blob/main/LICENSE , https://openobserve.ai/docs/enterprise-setup/enterprise-features/ , https://openobserve.ai/docs/enterprise-setup/license-and-pricing/
- Auth and TLS: built-in login, `ZO_HTTP_TLS_ENABLED` + cert/key paths, `ZO_CORS_ALLOWED_ORIGINS` for browsers. Source: environment-variables page above.
- Upgrade and backup: no upgrade guide page exists (the getting-started page only notes Cloud "handles ... upgrades for you"); retention via `ZO_COMPACT_DATA_RETENTION_DAYS`; backup of `ZO_DATA_DIR` or the S3 bucket is undocumented. Sources: https://openobserve.ai/docs/getting-started/ and environment-variables page.
- Product analytics: SQL panels with variables, filters and comparison; no funnel or session primitive. Source: https://openobserve.ai/docs/user-guide/dashboards/
- Browser RUM: the RUM app needs `@openobserve/browser-rum` + `@openobserve/browser-logs` posting to `/rum/v1/<org>/...`; plain OTel data appears in logs/traces but not in the RUM screens (cookie-based, per the earlier research). Source: https://openobserve.ai/docs/user-guide/data-exploration/rum/setup/

### 4. Grafana LGTM via Docker Compose

- OTLP: Loki's native endpoint `/otlp` (`/otlp/v1/logs`) unmarshals both `application/x-protobuf` and `application/json`; Mimir's `/otlp/v1/metrics` docs say Protocol Buffers, but the distributor switches on `jsonContentType` too; Tempo's distributor embeds Collector receivers (4317/4318, JSON). Grafana Alloy or the Collector in front gives one 4318 port with CORS and an `auth` hook. Sources: https://github.com/grafana/loki/blob/main/pkg/loghttp/push/otlp.go , https://grafana.com/docs/mimir/latest/references/http-api/ , https://github.com/grafana/mimir/blob/main/pkg/distributor/otel.go , https://grafana.com/docs/tempo/latest/configuration/ , https://grafana.com/docs/loki/latest/send-data/otel/
- Cloudflare exporter: works against Alloy/Collector behind an HTTPS proxy, or directly against Loki/Tempo if the proxy injects `X-Scope-OrgID` and auth.
- Stack and footprint: `grafana/otel-lgtm` bundles Grafana, Loki, Tempo, Prometheus, Pyroscope and a Collector in one image but is "intended for development, demo, and testing environments". A real Compose needs Grafana + Loki + Tempo + Mimir/Prometheus + Alloy (five processes). Loki's Docker install is for evaluation; Tempo's sizing page starts at 2 GB per distributor and 4 to 20 GB per live-store, with no monolithic hobby figure; Loki and Grafana publish none. Sources: https://github.com/grafana/docker-otel-lgtm , https://grafana.com/docs/loki/latest/setup/install/docker/ , https://grafana.com/docs/tempo/latest/setup/size/
- Multi-project: Loki, Tempo and Mimir are tenant-aware via `X-Scope-OrgID` but "Loki has no built-in authentication mechanism"; a reverse proxy must set and validate the header. Grafana OSS organisations can then hold one data source per tenant. Sources: https://grafana.com/docs/loki/latest/operations/multi-tenancy/ and Tempo configuration page (`multitenancy_enabled`).
- License: Grafana, Loki, Tempo and Mimir are AGPL-3.0; Alloy is Apache-2.0; `docker-otel-lgtm` is Apache-2.0. SAML, Team Sync and Active Sync are Enterprise/Cloud only; basic auth, anonymous, LDAP and OAuth (GitHub, Google, generic) are in OSS. Sources: https://github.com/grafana/grafana/blob/main/LICENSE , https://github.com/grafana/loki/blob/main/LICENSE , https://github.com/grafana/tempo/blob/main/LICENSE , https://github.com/grafana/mimir/blob/main/LICENSE , https://github.com/grafana/alloy/blob/main/LICENSE , https://grafana.com/docs/grafana/latest/setup-grafana/configure-security/configure-authentication/
- Auth and TLS: Grafana can terminate HTTPS itself (`protocol = https`, `cert_file`, `cert_key`); ingest TLS and auth live in Alloy or the proxy. Source: https://grafana.com/docs/grafana/latest/setup-grafana/set-up-https/
- Upgrade and backup: Grafana documents backing up `grafana.db`, config and plugins with the service stopped; Loki filesystem storage "is susceptible to data loss as it's unreplicated" and retention needs the compactor; Tempo local backend is monolithic-only. Each component upgrades independently. Sources: https://grafana.com/docs/grafana/latest/administration/back-up-grafana/ and https://grafana.com/docs/loki/latest/configure/storage/
- Product analytics: LogQL metric queries (`count_over_time`, `sum by`) and Logs Drilldown breakdowns by label/field give counts by attribute without SQL; there is no distinct-count function, so "sessions" means `count by (session_id)` then counting series, and funnels are dashboard math. Sources: https://grafana.com/docs/loki/latest/query/metric_queries/ and https://grafana.com/docs/grafana/latest/explore/simplified-exploration/logs/
- Browser RUM: plain OTel web SDK to Alloy/Collector; Grafana's own Faro was rejected in the spec.

### 5. Uptrace

- OTLP: OTLP/gRPC and OTLP/HTTP with per-signal `/v1/{traces,logs,metrics}`, auth via the `uptrace-dsn: https://<token>@<host>/<project_id>` header; self-hosted listens on 14317/14318. The docs recommend Protobuf, but the HTTP handlers for traces, logs and metrics switch on `jsonContentType` as well as `xprotobufContentType`/`protobufContentType`, so JSON is accepted. Sources: https://uptrace.dev/get/opentelemetry-python/otlp , https://github.com/uptrace/uptrace/blob/master/pkg/tracing/otlp_trace.go , https://github.com/uptrace/uptrace/blob/master/pkg/tracing/otlp_logs.go , https://github.com/uptrace/uptrace/blob/master/pkg/metrics/otlp.go
- Cloudflare exporter: works directly with the `uptrace-dsn` custom header over HTTPS.
- Stack and footprint: one Uptrace binary plus ClickHouse, PostgreSQL and Redis (the repo Compose also runs a Collector, Alertmanager, Vector, Keycloak, Grafana, Prometheus and Mailpit as extras). The only sizing table starts at 30 TB / 24 vCPU / 48 GB; no small figure. Sources: https://uptrace.dev/get/hosted , https://uptrace.dev/get/hosted/install , https://github.com/uptrace/uptrace/blob/master/docker-compose.yml
- Multi-project: first-class `projects` and `project_tokens` in `uptrace.yml` seed data, one DSN per project. Source: https://uptrace.dev/get/hosted/config
- License: AGPL-3.0 (GitHub license field and `LICENSE`); pricing says the Community Edition has "no limits", with Premium adding automation, custom retention and support. Sources: https://github.com/uptrace/uptrace/blob/master/LICENSE , https://uptrace.dev/pricing
- Auth and TLS: seeded users, optional `email_regexp` sign-up restriction, OIDC SSO in open source, TLS at `listen.tls` (cert/key). Source: config page above.
- Upgrade and backup: "Only upgrades to the next minor version are tested and supported"; procedure is backup both databases, install binary, run migrations, restart. Source: install page above.
- Product analytics: SQL-like span/log aggregation and PromQL-like metrics with a query builder and 50+ dashboards; no funnel primitive. Source: https://github.com/uptrace/uptrace
- Browser RUM: `@uptrace/web` is "a lightweight wrapper around opentelemetry-js"; plain OTel web SDK with the DSN header is the same wire. Source: https://uptrace.dev/get/opentelemetry-js/browser

## Recommendation

**Pick: self-hosted OpenObserve (open-source AGPL edition) on the VPS.** It is the only candidate that fits a 2 to 4 GB box as one process, has login, TLS and CORS as environment variables, gives each hobby project its own organisation without an enterprise licence, and takes OTLP JSON for all three signals directly from both the Effect layer (`Otlp.layerJson({ baseUrl: "https://o11y.example/api/<org>" })`) and the Cloudflare platform exporter (one destination per org and signal, `Authorization: Basic` header). Its weaknesses are documentation gaps (no published footprint, upgrade or local-disk backup guide) rather than missing capabilities; mitigate with a pinned image tag, a nightly `ZO_DATA_DIR` snapshot, and `ZO_COMPACT_DATA_RETENTION_DAYS=14`. Do not adopt its RUM SDK; keep the OTel web SDK and answer session and funnel questions with SQL panels over `event.name` and `session.id`.

**Fallback: SigNoz** on a 4 GB VPS if the query builder, trace funnels and the OTel-first UI matter more than per-project isolation. Separate projects by `service.namespace`/`service.name` filters, put Caddy or Traefik in front of 4318 for TLS and a shared-secret header, and follow the version-stop upgrade path. HyperDX is the runner-up if session replay becomes a want (MIT, four containers), but its OSS single-team model and 3-day default TTL make it a worse fit for "several projects, 14 days". Grafana LGTM is not recommended for one person on a small VPS: five AGPL components, no ingest auth without a proxy, and no monolithic sizing guidance. Uptrace is architecturally the cleanest multi-project design but needs three databases and publishes no small-deployment sizing.

**Grafana Cloud Free stays the stopgap.** Its limits (10k series, 50 GB logs, 50 GB traces, 14-day retention, 3 users; source: https://grafana.com/pricing/) cover several hobby projects, and because every candidate here speaks the same OTLP JSON, moving later is a change of `OTEL_EXPORTER_OTLP_ENDPOINT` and one header. Build no Grafana-specific panels you would mind rebuilding.

## Open questions

- Measured RAM and disk of OpenObserve at this project's volume (a few thousand log records and spans per day) is undocumented; run it for a week on the VPS with `ZO_MEM_TABLE_MAX_SIZE` capped and record RSS and `ZO_DATA_DIR` growth before committing other projects to it.
- OpenObserve's Basic auth puts an email:password pair into browser JavaScript; confirm whether the open-source edition supports a per-organisation service account or token with ingest-only rights, or whether the browser should post through a tiny Worker proxy that adds the header.
- Whether OpenObserve's OTLP metrics endpoint accepts a gauge with the `device.class` attribute as sent by the OTel web SDK (the metrics OTLP reference page returned 404 during research).
- Cloudflare's exporter needs one destination per signal and per project; check the dashboard limit on destinations per account before assuming one org per project.
- Mimir documents Protobuf only for `/otlp/v1/metrics` while the source accepts JSON; if LGTM is ever revisited, verify with a request rather than trusting either.

## Impact on docs/spec/observability.md

Nothing in the event model needs to change. Three additions keep it backend-neutral for a multi-project self-hosted backend:

1. Add `service.namespace=<project>` to every resource (server, indexer, browser). On OpenObserve the org already separates projects, but on SigNoz, HyperDX and shared-tenant setups this attribute is the only separation, and it costs nothing.
2. State that the backend must accept OTLP/HTTP JSON for traces, logs and metrics and expose CORS for the site origin; note that the Cloudflare destination URL must include the full `/v1/traces` or `/v1/logs` path, and that the browser's auth header is public, so the credential must be ingest-only and per project.
3. Under Backend, record that funnels and sessions are dashboard queries over `event.name` and `session.id` (no candidate provides them natively over log records), so the `session.id` resource attribute and the `turn.id` attribute on `prompt_submitted`, `turn_finished`, `turn_error` and `citation_clicked` are the join keys and must stay stable.
